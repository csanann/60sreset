## 2026-10-23 — Ticket 1.3B: controlled server-side Gemini integration

- Contract first: a reset now contains a short reflection, a balanced perspective and optionally one next step. Runtime parsing rejects missing/blank/wrong-type/oversized/extra fields; TypeScript and a provider JSON schema do not replace validation of untrusted model output. Safety is a separate fixed-copy branch with no normal reframe fields.
- Server flow: validate POST JSON and input/request sizes, run the early danger gate, check mode/key/development state, reserve quota, call Gemini once, validate completion/safety/schema/content, then return a labelled response or fixed error. Client validation improves feedback; the server remains authoritative. The client supports structured mock, Gemini and safety responses without importing server modules.
- Provider request: one REST `generateContent` request to `gemini-2.5-flash-lite`, API key in a server-only header, one candidate, 512 output tokens, thinking budget 0, an 8-second deadline covering reads and a 32 KiB response-byte cap. No tools/history, SDK retries, redirects, repair call or fallback. The app still makes one request per button press and aborts after 10 seconds/unmount.
- Explicit owner scope: mock mode remains default and requires no key/quota; Gemini is only enabled explicitly in local development. The owner selected **10 attempts per UTC day**. Production Gemini is rejected even if a key exists. No real credential file is created, printed or committed.
- Fail-closed quota: initialize an ignored local aggregate file once. Reserve durably under an exclusive filesystem lock before contacting the provider. Crashes, timeouts and ambiguous failures never refund a slot. Missing/corrupt/locked state, incomplete writes or a backwards clock deny requests. Normal UTC day rollover resets the count. The file contains only version/date/count, never thoughts, output, keys or user identifiers.
- Necessary complexity: locking plus synchronized atomic replacement keeps concurrent local requests from racing past the cap and survives dev-server restarts. Separate clones, paths, hosts or isolated instances do not share that cap; the owner can still tamper with local state. It is not production/distributed enforcement. Server policy, provider transport and quota logic are separated so tests can replace network calls while exercising the real HTTP route.
- Safety: explicit English danger phrases are checked before quota/provider access, including in mock mode. Strong sadness, anxiety, anger or profanity alone does not trigger the gate. Provider blocks, model safety dispositions and recognized unsafe generated advice use fixed support copy. Heuristics can miss paraphrases/languages or misread quotes/negation; schema-valid content can still be wrong or unsafe. This is not a clinical classifier, diagnosis or treatment feature.
- Privacy: the app adds no thought/output/key logging or storage, authentication, database or analytics. Google processing/retention is separate from application non-retention; fictional text only until provider/account handling is reviewed. No provider request is made by the automated tests. The optional real smoke test still requires explicit owner approval and is limited to one fictional request.

## 2026-10-18 — Ticket 1.3A: completed mock endpoint and learning notes

- Practised: Expo Router `+api.ts` routes, POST JSON contracts, independent server validation, asynchronous screen state, cancellation and safe error handling.
- HTTP vocabulary: POST is the request method used to submit the text; `/api/reset` is the endpoint path; JSON is the request/response data format. The client sends `{ "thought": "Synthetic test thought" }` with `Content-Type: application/json`; the server replies with `mock`, `label` and `reflection`, or a fixed error and HTTP status.
- Workflow: `index.tsx` handles the form/state, `request-reset.ts` sends the request and checks its response, `reset+api.ts` runs server-side validation and returns the fixed mock, and `reset-contract.ts` holds shared input rules. Client checks help UX; server checks enforce the contract against callers who bypass the UI. TypeScript checks development-time types; untrusted JSON still needs runtime validation.
- Architecture/styling: frontend and server code can share a repository while running separately. `.web.tsx` selects a browser-specific React component; the existing web tabs are currently unused. React Native style objects support cross-platform components, while this project's `global.css` contains browser font variables. Shared colours/spacing belong in the theme; component-specific layout can stay beside the component.
- Research: checked installed Expo SDK 57 against its versioned documentation and the Expo docs index/API-route guide. SDK 57 needs server output; native relative fetch uses the development server origin. Production native requires a hosted server/origin later.
- Implementation: `POST /api/reset` accepts exactly one string `thought`, validates non-whitespace and at most 2,000 original UTF-16 code units, and limits streamed JSON to 16 KiB. It returns the same labelled mock for every valid thought. Reset shows loading/success/error, prevents duplicate requests, times out after 10 seconds and cancels on unmount.
- Privacy: no external AI, thought logging or persistence; no secrets, environment variables, authentication, database, analytics or dependencies added. Text is now transmitted to the app server in a POST body, which the screen discloses. Responses do not echo it, and successful/error responses use `no-store`.
- API key protection: a future provider key belongs in server-only hosting secret configuration and must only be used by the route/server-only modules. Keep it out of client imports, shared contracts, `EXPO_PUBLIC_` variables, public app configuration, Git, logs and responses. Server-only execution protects the credential from client bundles; access/abuse and cost controls would still need a separate review before a real provider. This mock has no key or provider call. References: [Expo API route security](https://docs.expo.dev/router/web/api-routes/#security), [Expo environment variables](https://docs.expo.dev/guides/environment-variables/).
- Tests: 40 passing Node built-in tests exercise input types/shape, empty/whitespace and length boundaries, escaped input, Unicode chunk boundaries, malformed JSON/content type, streamed body limits without trusting Content-Length, no logging, sanitized server/network/protocol errors, cancellation and timeout cleanup. Node module-detection and experimental mock-timer warnings are expected on the pinned runtime.
- Verification: lint, typecheck and production web/server export passed. Typecheck exposed an existing `/explore` link in unused web tabs after the prior route deletion; removed only that stale link. Final review strengthened the client validation test to require the correct validation message and zero network calls, preventing a false pass when request errors are caught.
- HTTP verification: served the exported bundle locally with Expo. Synthetic valid POST returned 200 with the mock label and `no-store`; whitespace, wrong type, excessive thought length and malformed JSON returned 400; excessive body bytes returned 413; unsupported content type returned 415; GET returned 405. Screen returned 200 with the input limit and Reset button. The temporary server was stopped. Localhost access required sandbox escalation.

These were user-run browser checks, not automated UI tests or independent device verification.
- Limit/UX distinction: the server counts 2,000 UTF-16 code units, including surrounding whitespace, rather than 2,000 words. Some emoji take two code units. The input caps entry and explains the limit; a live counter or limit notice remains a possible later UX improvement, not part of this implementation.
